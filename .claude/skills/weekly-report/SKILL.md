# 週報を書く

- **締切**: 毎週月曜 正午（JST）
- **対象期間**: 9/24 - 11/7
- **提出**: 手で貼る。**Actions で自動化しない**（内容の半分が GitHub の外にあるため）

**読むのはこのリポジトリを見ていない人。** Issue 番号を出しても誰も引けないし、
`cron` や `Actions` と書いても伝わらない。ここが一番の勘所で、下の「5. 書くときのルール」が
このスキルの本体。GitHub から情報を集める部分は手段にすぎない。

## 0. できあがりの形

```markdown
# 期間：9/24 - 11/7

### 共有すること：
- （GitHub に出ない話。無ければ見出しごと落とさず「特になし」と書く）

### 先週やったこと ✅（M/D - M/D）

- **やったことを動詞で言い切る見出し**
  - 背景や結果を2〜4行
  - 数字は実測のみ
- **もう1件**
  - 同上

### 今週やること ✍️（M/D - M/D）

- **やることを動詞で言い切る見出し**（担当：自分）
  - どこまでやったら終わりかを1〜2行

### 困りごとや相談したいこと🆘
- （無ければ「なし！引き続き楽しみつつ、頑張りつつ！」のように明るく締める）
```

見出しは `###` で揃える。絵文字（✅ ✍️ 🆘）は運営指定の形なので落とさない。

## 1. 週の範囲を出す

月曜に書く前提。**先週 = 前週の月〜日、今週 = 今日から日曜**。

```bash
DOW=$(date +%u)                                   # 月=1
LAST_MON=$(date -v-$((DOW-1+7))d '+%-m/%-d')
LAST_SUN=$(date -v-$((DOW-1+1))d '+%-m/%-d')
THIS_MON=$(date -v-$((DOW-1))d '+%-m/%-d')
THIS_SUN=$(date -v+$((7-DOW))d '+%-m/%-d')
SINCE=$(date -v-$((DOW-1+7))d +%F)                # 絞り込み用（ISO）
echo "先週 $LAST_MON - $LAST_SUN / 今週 $THIS_MON - $THIS_SUN"
```

月曜以外に書く場合も「直近の月曜」を今週の起点にする。

**締切直前に終わった作業は先週側に入れてよい。** 日付の帳尻より「どの週の仕事か」で判断する。

## 2. 先週の実績を集める

```bash
ME=$(gh api user -q .login)

# マージされた PR
gh pr list --state merged --limit 60 --json number,title,mergedAt,author \
  -q ".[] | select(.author.login==\"$ME\") | select(.mergedAt >= \"$SINCE\") | \"\(.mergedAt[0:10]) #\(.number) \(.title)\""

# 閉じた Issue
gh issue list --state closed --limit 60 --assignee @me --json number,title,closedAt \
  -q ".[] | select(.closedAt >= \"$SINCE\") | \"\(.closedAt[0:10]) #\(.number) \(.title)\""

# 立てた Issue・書いたコメント（調査や方針出しはここにしか残らない）
gh issue list --state all --limit 60 --author @me --json number,title,createdAt \
  -q ".[] | select(.createdAt >= \"$SINCE\") | \"\(.createdAt[0:10]) #\(.number) \(.title)\""
gh search issues --repo yuai-project/yuai --commenter "$ME" --limit 20 \
  --json number,title,updatedAt -q '.[] | "\(.updatedAt[0:10]) #\(.number) \(.title)"' | sort -r
```

**PR だけ見ると調査系の仕事が丸ごと消える。** 方針を決めた・論点を整理したといった
成果は Issue 本文とコメントにしか残らないので、必ず拾う。

**GitHub の時刻は UTC。** JST は +9 時間なので、15:00 UTC 以降の活動は日本時間では翌日。
週の境目にある活動は、この9時間で先週/今週が入れ替わる。

数字（何日連続で動いた、何時間遅れた等）を書くときは、**推測せず実際に調べる**:

```bash
gh run list --workflow=<name>.yml --limit 15 --json createdAt,conclusion,event
```

## 3. 今週やることを取る

[ボード](https://github.com/orgs/yuai-project/projects/1)の自分のカードを見る。

```bash
gh project item-list 1 --owner yuai-project --limit 300 --format json | ME="$ME" python3 -c "
import json, sys, os
me = os.environ['ME']
for i in json.load(sys.stdin)['items']:
    c = i.get('content', {})
    if me in (i.get('assignees') or []) and i.get('status') != 'Done':
        print(i.get('status'), '#%s' % c.get('number'), c.get('title'))
"
```

- `In Progress` / `Todo` の自分担当 → そのまま今週やること
- `In Review` に残っているもの → 完了条件が埋まっていないことが多い。何を確かめたら
  閉じられるかを1行で書く
- `Backlog` から上げるものがあれば、**やると決めたことをボードにも反映する**
  （週報だけ前のめりになってボードが古いままだと、他の3人から見えない）

## 4. GitHub に無いことを聞く

**ここを飛ばさない。勝手に書かない。** 週報の「共有すること」と「困りごと」は
GitHub のどこにも無く、聞かないと分からない。1回でまとめて聞く。

- 先週、GitHub に残っていない作業はなかったか（打ち合わせ・調査・読んだ資料・イベント）
- 共有したいことはあるか（勉強会で誰と会った、提出が遅れた、来週の予定など）
- 困りごと・相談したいことはあるか

困りごとが無ければ**無理に作らない**。「なし！」のように明るく締めてよい。
逆に、手が止まっている案件があるなら、誰の何待ちかまで書くと動く。

## 5. 書くときのルール

読み手は GitHub を見ていない。**これを読んで意味が通るかだけを基準にする。**

- **Issue 番号・PR 番号を本文に書かない。** 「#96」は読み手には何の情報もない
- **ツール名・専門用語を開く**
  - cron が発火しない → 「毎日決まった時刻に動くはずの処理が動かない」
  - Actions → 「自動実行の仕組み」 / モック → 「仮データ」 / スキーマ → 「データの持ち方」
  - 自社プロダクトの機能名は、初出で何をするものか1行添える
    （例: 記事レコメンド機能（相談フォームの入力に合わせて記事を出す））
- **1項目 = 太字の見出し1行 + サブ箇条書き2〜4行。** 見出しだけ読んで週の全体像がつかめること
- **見出しは動詞で言い切る。** 「日報の件」ではなく「日報の自動投稿が動かない問題を修正」
- **「調査した」で終わらせない。** 何が分かって、どう決めたかまで書く
- **不採用にした案と、その理由は書く価値がある。** 判断の質が伝わるのはここ
- **数字は実測のみ。** 「7日連続で自動投稿されている」は調べた事実。盛らない
- **1セクション4項目前後。** 全部書くと読まれない。小さい作業はまとめる
- **今週やることに他人の担当を混ぜない。** 混ぜるなら「（担当：◯◯さん）」と明記する

## 6. 仕上げ

チャットに Markdown をそのまま出す。**そのままコピペできる状態にする**（提出は手作業）。

書いたあとに1回だけ通しで読み、次を確認する:

- [ ] Issue 番号・PR 番号が本文に残っていないか
- [ ] リポジトリを見ていない人が読んで、意味の分からない単語が無いか
- [ ] 先週の項目が、実際に GitHub か本人の申告で裏が取れているか（捏造しない）
- [ ] 困りごとが空欄のまま放置されていないか

期間（9/24 - 11/7）を過ぎたら、このスキルの冒頭を更新するか、使うのをやめる。
